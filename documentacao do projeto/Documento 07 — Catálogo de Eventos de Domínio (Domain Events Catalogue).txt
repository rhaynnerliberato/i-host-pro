Documento 07
Catálogo de Eventos de Domínio (Domain Events Catalogue)

Versão: 1.0

Status: Oficial

1. Objetivo

Este documento define todos os eventos oficiais do domínio do iHostPro.

Os eventos representam fatos ocorridos dentro da plataforma e constituem o principal mecanismo de comunicação entre módulos.

Todo comportamento automatizado deverá ser iniciado pela publicação de um ou mais eventos de domínio.

Nenhum módulo deverá executar lógica de negócio pertencente a outro módulo através de chamadas diretas quando existir um evento equivalente.

2. Princípios

Todo evento representa um fato consumado.

Um evento:

nunca representa uma intenção;
nunca representa um comando;
nunca representa uma solicitação.

Eventos representam apenas algo que realmente aconteceu.

Exemplos corretos:

ReservaConfirmada
FaxinaConcluida
PixRecebido

Exemplos incorretos:

CriarFaxina
EnviarSenha
AtualizarAgenda

Esses são comandos, não eventos.

3. Estrutura Padrão de um Evento

Todo evento deverá possuir obrigatoriamente os seguintes campos:

Campo	Obrigatório	Descrição
EventId	Sim	Identificador único
EventName	Sim	Nome oficial do evento
AggregateId	Sim	Identificador da entidade principal
AggregateType	Sim	Tipo da entidade
TenantId	Sim	Cliente proprietário
Timestamp	Sim	Data e hora UTC
Version	Sim	Versão do evento
CorrelationId	Sim	Identificador da operação
CausationId	Sim	Evento que originou este
ActorType	Sim	Usuário, IA, Sistema, Integração
ActorId	Opcional	Identificador do ator
Payload	Sim	Dados do evento
4. Convenção de Nomenclatura

13.1 Payloads dos Eventos do Incremento 2 (Login, JWT, Refresh Token, Logout)

Implementados na Etapa 15 do Incremento 2 (ver ADR-013 para a convenção de roteamento RabbitMQ). Nenhum destes eventos inclui e-mail, endereço IP, User-Agent, senha, access token, refresh token, hash de token ou qualquer outro segredo — apenas identificadores e códigos estáveis.

Convenção comum a todos os seis, além dos campos obrigatórios do envelope (Seção 3):

- AggregateType/AggregateId representam o Usuário (AggregateId = userId) em todos os seis eventos, exceto LoginFailed, cujo AggregateType/AggregateId representam o Tenant (AggregateId = tenantId) — o único caso em que o usuário pode não existir (ex.: e-mail não cadastrado), enquanto o tenant já foi resolvido antes deste evento poder ser publicado.
- ActorType é sempre "User" (o fato é sempre desencadeado por uma requisição de um cliente, mesmo quando rejeitada ou classificada pelo sistema). ActorId é o userId quando conhecido, ausente quando não (LoginFailed com usuário não encontrado).
- Quando dois eventos são publicados pela mesma operação (LoginFailed+AccountLockedOut; UserLoggedOut+SessionRevoked; RefreshTokenReuseDetected+SessionRevoked), o segundo evento da dupla preenche CausationId com o EventId do primeiro.

UserLoggedIn
| Campo | Tipo | Descrição |
|---|---|---|
| SessionId | Guid | Sessão criada por este login |

LoginFailed
| Campo | Tipo | Descrição |
|---|---|---|
| UserId | Guid? | Nulo quando o e-mail não corresponde a nenhum usuário do tenant |
| ReasonCode | string | Código ASCII estável — ver tabela de códigos abaixo |

Códigos de ReasonCode para LoginFailed:
| Código | Situação |
|---|---|
| user_not_found | Nenhum usuário com este e-mail no tenant |
| user_blocked | Usuário existe, está com status Blocked |
| invalid_password | Senha incorreta — usado tanto quando a tentativa não atinge o limiar de bloqueio quanto na própria tentativa que o atinge (neste segundo caso, acompanhado de AccountLockedOut na mesma operação) |
| account_locked | Conta já estava bloqueada por tentativas anteriores (distinto de AccountLockedOut, que representa a tentativa que efetivamente inicia o bloqueio) |

AccountLockedOut
| Campo | Tipo | Descrição |
|---|---|---|
| LockoutEnd | DateTimeOffset (UTC) | Instante em que o bloqueio expira |
| ReasonCode | string | Código ASCII estável — ver tabela de códigos abaixo |

Códigos de ReasonCode para AccountLockedOut:
| Código | Situação |
|---|---|
| max_failed_attempts | Número de tentativas de senha incorreta atingiu o limiar configurado (único gatilho existente neste incremento) |

UserLoggedOut
| Campo | Tipo | Descrição |
|---|---|---|
| SessionId | Guid | Sessão encerrada por este logout |

RefreshTokenReuseDetected
| Campo | Tipo | Descrição |
|---|---|---|
| SessionId | Guid | Sessão cuja cadeia de rotação foi invalidada |
| TokenId | Guid | Identificador público do refresh token reutilizado (nunca o hash ou o token completo) |

SessionRevoked
| Campo | Tipo | Descrição |
|---|---|---|
| SessionId | Guid | Sessão revogada |
| ReasonCode | string | Código ASCII estável — ver tabela de códigos abaixo |

Códigos de ReasonCode para SessionRevoked (únicos gatilhos existentes neste incremento):
| Código | Situação |
|---|---|
| logout_requested | Revogação por logout explícito |
| refresh_token_reuse_detected | Revogação por reutilização de refresh token já rotacionado, fora da janela de graça |

13.2 Roteamento RabbitMQ dos Eventos do Incremento 2

Ver ADR-013 (Convenção de Roteamento RabbitMQ para Integration Events) para a decisão completa. Resumo: exchange único por Bounded Context, tipo topic, routing key = nome do evento em snake_case.

| Evento | Exchange | Routing Key |
|---|---|---|
| UserLoggedIn | identity-events | user_logged_in |
| LoginFailed | identity-events | login_failed |
| AccountLockedOut | identity-events | account_locked_out |
| UserLoggedOut | identity-events | user_logged_out |
| RefreshTokenReuseDetected | identity-events | refresh_token_reuse_detected |
| SessionRevoked | identity-events | session_revoked |

19. Versionamento

Eventos nunca poderão ser alterados após publicação.

Caso seja necessário modificar sua estrutura:

Criar nova versão.

Exemplo:

ReservationCreatedV2

Preservando compatibilidade.

20. Idempotência

Todo consumidor deverá suportar o processamento repetido do mesmo evento.

Processar o mesmo evento duas vezes nunca poderá produzir efeitos duplicados.

21. Garantias

A plataforma deverá garantir:

publicação confiável;
processamento assíncrono;
rastreabilidade;
reprocessamento;
ordenação quando necessária;
isolamento entre consumidores.
22. Eventos Proibidos

Nunca criar eventos que representem:

consultas;
comandos;
intenções;
validações intermediárias.

Eventos representam apenas fatos consumados.

23. Auditoria

Todo evento deverá gerar automaticamente um registo de auditoria contendo:

evento;
data;
origem;
utilizador;
entidade afetada;
resultado;
correlação.
24. Evolução do Catálogo

Novos eventos deverão:

representar um facto de negócio;
possuir consumidores identificados;
ser documentados neste catálogo antes da implementação;
manter compatibilidade com versões anteriores.

Nenhum evento poderá ser introduzido diretamente no código sem atualização deste documento.
