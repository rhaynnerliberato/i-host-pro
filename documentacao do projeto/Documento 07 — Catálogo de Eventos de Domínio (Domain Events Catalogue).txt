Documento 07
Catálogo de Eventos de Domínio (Domain Events Catalogue)

Versão: 1.0

Status: Oficial

1. Objetivo

Este documento define todos os eventos oficiais do domínio do iHostPro.

Os eventos representam fatos ocorridos dentro da plataforma e constituem o principal mecanismo de comunicação entre módulos.

Todo comportamento automatizado deverá ser iniciado pela publicação de um ou mais eventos de domínio.

Nenhum módulo deverá executar lógica de negócio pertencente a outro módulo através de chamadas diretas quando existir um evento equivalente.

2. Princípios

Todo evento representa um fato consumado.

Um evento:

nunca representa uma intenção;
nunca representa um comando;
nunca representa uma solicitação.

Eventos representam apenas algo que realmente aconteceu.

Exemplos corretos:

ReservaConfirmada
FaxinaConcluida
PixRecebido

Exemplos incorretos:

CriarFaxina
EnviarSenha
AtualizarAgenda

Esses são comandos, não eventos.

3. Estrutura Padrão de um Evento

Todo evento deverá possuir obrigatoriamente os seguintes campos:

Campo	Obrigatório	Descrição
EventId	Sim	Identificador único
EventName	Sim	Nome oficial do evento
AggregateId	Sim	Identificador da entidade principal
AggregateType	Sim	Tipo da entidade
TenantId	Sim	Cliente proprietário
Timestamp	Sim	Data e hora UTC
Version	Sim	Versão do evento
CorrelationId	Sim	Identificador da operação
CausationId	Sim	Evento que originou este
ActorType	Sim	Usuário, IA, Sistema, Integração
ActorId	Opcional	Identificador do ator
Payload	Sim	Dados do evento
4. Convenção de Nomenclatura

Todos os eventos deverão utilizar:

Exemplos:

13.1 Payloads dos Eventos do Incremento 2 (Login, JWT, Refresh Token, Logout)

Implementados na Etapa 15 do Incremento 2 (ver ADR-013 para a convenção de roteamento RabbitMQ). Nenhum destes eventos inclui e-mail, endereço IP, User-Agent, senha, access token, refresh token, hash de token ou qualquer outro segredo — apenas identificadores e códigos estáveis.

Convenção comum a todos os seis, além dos campos obrigatórios do envelope (Seção 3):

- AggregateType/AggregateId representam o Usuário (AggregateId = userId) em todos os seis eventos, exceto LoginFailed, cujo AggregateType/AggregateId representam o Tenant (AggregateId = tenantId) — o único caso em que o usuário pode não existir (ex.: e-mail não cadastrado), enquanto o tenant já foi resolvido antes deste evento poder ser publicado.
- ActorType é sempre "User" (o fato é sempre desencadeado por uma requisição de um cliente, mesmo quando rejeitada ou classificada pelo sistema). ActorId é o userId quando conhecido, ausente quando não (LoginFailed com usuário não encontrado).
- Quando dois eventos são publicados pela mesma operação (LoginFailed+AccountLockedOut; UserLoggedOut+SessionRevoked; RefreshTokenReuseDetected+SessionRevoked), o segundo evento da dupla preenche CausationId com o EventId do primeiro.

13.3 Payloads dos Eventos do Incremento 3, Checkpoint 1 (Gestão de Usuários e Sessões)

Contratos e vocabulário de códigos definidos no Checkpoint 1 do Incremento 3 do contexto Identity & Access (autorização RBAC+ABAC e gestão de usuários/sessões). UserCreated é publicado desde o Checkpoint 5, pelo CreateUserCommand (POST /api/v1/users). UserRoleAssigned é publicado desde o Checkpoint 5 (pelo mesmo CreateUserCommand, para o papel inicial obrigatório) e também desde o Checkpoint 6, pelo AssignRoleCommand (POST /api/v1/users/{userId}/roles). UserRoleRemoved é publicado desde o Checkpoint 6, pelo RemoveRoleCommand (DELETE /api/v1/users/{userId}/roles/{roleCode}). UserBlocked é publicado desde o Checkpoint 7, pelo BlockUserCommand (POST /api/v1/users/{userId}/block); UserUnblocked também desde o Checkpoint 7, pelo UnblockUserCommand (POST /api/v1/users/{userId}/unblock). UserUpdated é publicado desde o Checkpoint 8, pelo UpdateUserCommand (PATCH /api/v1/users/{userId}) — somente quando pelo menos um campo efetivamente muda (Seção 4 da decisão do Checkpoint 8: idempotência). PasswordChanged é publicado desde o Checkpoint 9, pelo ChangeOwnPasswordCommand (POST /api/v1/users/me/change-password, ChangeType = self) e pelo AdminResetPasswordCommand (POST /api/v1/users/{userId}/reset-password, ChangeType = admin_reset). Nenhum destes eventos inclui e-mail, endereço IP, User-Agent, senha, hash de senha, access token, refresh token, hash de token ou qualquer outro segredo — apenas identificadores e códigos estáveis, mesma regra do §13.1.

Convenção comum aos sete:

- AggregateType/AggregateId representam o Usuário afetado (AggregateId = userId) em todos os sete eventos.
- ActorType é sempre "User". ActorId é o id do Administrador que executou a ação — exceto em PasswordChanged com ChangeType = self, em que ActorId é o próprio usuário afetado (o mesmo valor de AggregateId). É por isso que nenhum destes sete eventos possui um campo próprio como CreatedByUserId, BlockedByUserId, AssignedByUserId ou equivalente — ActorId já é o campo padrão do envelope (Seção 3) para "quem executou a ação"; repeti-lo com outro nome em cada evento seria duplicação.
- UserCreated é sempre publicado na mesma transação que um UserRoleAssigned para o papel inicial obrigatório (Seção 5 da decisão do Incremento 3: não é permitido criar usuário sem papel) — o CausationId de UserRoleAssigned preenche o EventId de UserCreated.
- UserBlocked, UserRoleAssigned, UserRoleRemoved e PasswordChanged são sempre publicados na mesma transação que um SessionRevoked por sessão ativa revogada em cascata (ver §13.1) — cada SessionRevoked preenche CausationId com o EventId do evento primário correspondente.
- Nenhum destes eventos é publicado quando a operação não altera estado efetivamente (ex.: atribuir um papel já atribuído, bloquear um usuário já bloqueado) — ver as regras de idempotência aprovadas no planejamento do Incremento 3.

|---|---|---|
| (nenhum campo próprio) | — | AggregateId já identifica o usuário criado; o papel inicial é informado pelo UserRoleAssigned publicado na mesma transação |

|---|---|---|
| (nenhum campo próprio) | — | AggregateId já identifica o usuário desbloqueado; nunca restaura sessões revogadas pelo UserBlocked anterior |

|---|---|---|
| RoleCode | string | Código estável do papel (ex.: "ADMIN") — nunca o nome de exibição |

|---|---|---|

PasswordChanged

|---|---|---|

14.1 Payloads dos Eventos do Incremento 1 (Fase 2), Checkpoints 2, 3 e 4 (Condomínios, Imóveis administrativos e Lifecycle de Imóveis)

Implementados nos Checkpoints 2 (Condomínios), 3 (Imóveis administrativos) e 4 (Lifecycle de Imóveis) do Incremento 1 da Fase 2 (Property Management). Nenhum destes sete eventos inclui nome, endereço, CEP, capacidade, código do imóvel, id do condomínio (antigo ou novo), status anterior ou qualquer outro dado de negócio — apenas identificadores e, quando aplicável, códigos estáveis de campo alterado, mesma regra do §13.1/§13.3.

Convenção comum aos sete:

- AggregateType/AggregateId representam o Condomínio (CondominiumCreated/CondominiumUpdated) ou o Imóvel (todos os demais) afetado.

- PropertyActivated/PropertyDeactivated/PropertyArchived são publicados exatamente uma vez por transição de estado efetivamente confirmada — nunca em uma rejeição (transição inválida, estado já no destino, conflito de concorrência) — ver Checkpoint 4, §3/§4.

14.3 Payloads dos Eventos do Checkpoint 5 (Ownership de Imóveis)

Implementados no Checkpoint 5 do Incremento 1 da Fase 2 (Property Management) — vínculo/desvínculo entre um usuário do contexto Identity & Access e um Imóvel. Nenhum destes dois eventos inclui nome, e-mail, papel, status ou qualquer outro dado pessoal do proprietário, nem qualquer dado do Imóvel (código, nome, endereço) — apenas identificadores, mesma regra do §13.1/§13.3/§14.1.

Convenção comum aos dois:

- AggregateType/AggregateId representam o Imóvel afetado (AggregateId = PropertyId), nunca o Owner.
- TenantId (envelope, Seção 3) já identifica o tenant — nenhum campo próprio redundante.
- ActorType é sempre "User". ActorId é o id do Administrador que executou o vínculo/desvínculo (PROPERTIES:MANAGE) — nunca o próprio Owner (este Checkpoint não expõe nenhuma ação de escrita ao Owner).
- Publicados exatamente uma vez por vínculo/desvínculo efetivamente confirmado — nunca em uma rejeição (usuário inexistente/inelegível, Imóvel inexistente, vínculo já existente/inexistente) — ver Checkpoint 5, item 15.
- O vínculo/desvínculo é permitido para um Imóvel em qualquer status (Draft/Active/Inactive/Archived) — estes dois eventos nunca alteram, e nunca dependem de, PropertyStatus.

|---|---|---|
| PropertyId | Guid | Redundante com AggregateId |
| OwnerUserId | Guid | Identificador opaco do usuário do contexto Identity & Access vinculado como proprietário — nunca nome/e-mail/papel |

|---|---|---|

Um único evento poderá originar diversos outros.

Exemplo:

↓

CleaningCreated

↓

CleaningAssigned

↓

↓

↓

20. Versionamento

Eventos nunca poderão ser alterados após publicação.

Caso seja necessário modificar sua estrutura:

Criar nova versão.

Exemplo:

ReservationCreatedV2

Preservando compatibilidade.

21. Idempotência

Todo consumidor deverá suportar o processamento repetido do mesmo evento.

Processar o mesmo evento duas vezes nunca poderá produzir efeitos duplicados.

22. Garantias

A plataforma deverá garantir:

publicação confiável;
processamento assíncrono;
rastreabilidade;
reprocessamento;
ordenação quando necessária;
isolamento entre consumidores.
23. Eventos Proibidos

Nunca criar eventos que representem:

consultas;
comandos;
intenções;
validações intermediárias.

Eventos representam apenas fatos consumados.

24. Auditoria

Todo evento deverá gerar automaticamente um registo de auditoria contendo:

evento;
data;
origem;
utilizador;
entidade afetada;
resultado;
correlação.
25. Evolução do Catálogo

Novos eventos deverão:

representar um facto de negócio;
possuir consumidores identificados;
ser documentados neste catálogo antes da implementação;
manter compatibilidade com versões anteriores.

Nenhum evento poderá ser introduzido diretamente no código sem atualização deste documento.

Os demais eventos listados no §5 (ReservationConfirmed, GuestCheckedIn, GuestCheckedOut, ReservationClosed) permanecem prospectivos, sem payload/roteamento definidos até serem implementados em fase futura (ver Plano Executivo de Desenvolvimento por Fases, Fase 10).

Anexado como seção nova ao final do documento — deliberadamente não inserido como subseção do §14 (que é específico do módulo Property Management) e sem renumerar nenhuma seção existente, preservando as referências já registradas em outros documentos (ex.: ADR-013 cita §13.2/§19).

27.1 Payloads dos Eventos do Incremento 1 (Fase 3)

Nenhum dos três eventos inclui nome do hóspede, telefone do hóspede, quantidade de hóspedes, ou qualquer valor anterior/posterior de campo alterado — apenas identificadores e, para ReservationUpdated, códigos estáveis de campo alterado — mesma regra do §13.1/§13.3/§14.1/§14.3. **Atualizado pela Fase 7, Incremento 2 (Dashboard & Reporting Foundation), Checkpoint 0/1 — ver §27.3**: ReservationCreated/ReservationUpdated passaram a incluir CheckInAt/CheckOutAt (a dimensão temporal operacional, nunca PII) — datas de check-in/check-out não fazem mais parte da lista de conteúdo permanentemente excluído.

Convenção comum aos três:

- AggregateType/AggregateId representam a Reserva afetada (AggregateId = ReservationId).
- ActorType é sempre "User". ActorId é o id do Administrador/Operador que executou a ação (RESERVATIONS:MANAGE).
- ReservationUpdated nunca é publicado quando a operação não altera estado efetivamente (PATCH idempotente — nenhum campo suprido difere, após normalização, do valor atual), nem quando a atualização é rejeitada por conflito de concorrência (snapshot desatualizado) — ver Fase 3 §3.
- ReservationCancelled é publicado exatamente uma vez por cancelamento efetivamente confirmado — nunca em uma rejeição (reserva inexistente, já cancelada).

27.3 Amendment — Fase 7, Incremento 2 (Dashboard & Reporting Foundation), Checkpoint 0/1

Decisão do usuário (Checkpoint 0, decisão 2): alteração aditiva aprovada em ReservationCreated/ReservationUpdated para transportar CheckInAt/CheckOutAt — a dimensão temporal operacional que o novo Bounded Context Dashboard & Reporting precisa para materializar indicadores de check-ins/check-outs/reservas futuras/canceladas sem se tornar um HTTP aggregator sobre Reservations (Architecture Principles §14 — Dashboard & Reporting é um contexto terminal, apenas consome eventos). GuestName/GuestPhone/GuestCount permanecem permanentemente excluídos — nenhuma decisão os aprovou.

Compatibility gate executado antes da alteração: verificado que o único consumidor real de ReservationCreated/ReservationCancelled (Housekeeping, `ReservationProjectionAndCancellationReaction`) lê exclusivamente TenantId/ReservationId/EventId/CorrelationId — nunca PropertyId/Status, e certamente nunca os novos campos — tornando a alteração aditiva segura sem exigir nenhuma migração de consumer existente. `ReservationUpdated` não tinha, até este checkpoint, nenhum consumidor real no código (`IIntegrationEventHandler<ReservationUpdated>` não existia em lugar nenhum), tornando essa alteração ainda mais segura. Serializador (System.Text.Json, via Wolverine) ignora campos desconhecidos por padrão — compatível em ambas as direções (consumidor novo lendo envelope antigo recebe `null`; consumidor antigo lendo envelope novo ignora os campos extras). Nenhum `ReservationCreatedV2` foi criado — desnecessário dado que a alteração é puramente aditiva e compatível.

`CleaningDelayed` não é consumido pela Agenda porque não altera `Cleaning.Status` nem qualquer outro campo materializado pela projeção — `ReportOwnCleaningDelayCommandHandler` nunca chama um método de transição de `Cleaning`, apenas publica uma notificação. Consumi-lo seria um no-op sem efeito observável. Não foi inventada uma nova data por inferência a partir deste evento.
