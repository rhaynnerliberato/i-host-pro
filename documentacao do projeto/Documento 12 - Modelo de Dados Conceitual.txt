Documento 12 - Modelo de Dados Conceitual

Versão: 1.0

Status: Oficial

1. Objetivo

Este documento define o modelo conceitual de dados do iHostPro.

Seu objetivo não é especificar tabelas, índices ou tipos de dados.

O objetivo é representar o domínio de negócio da plataforma, as entidades principais, seus relacionamentos e regras de consistência.

A definição do modelo físico, do tipo de banco de dados e das estratégias de persistência será responsabilidade do Claude Code, respeitando este modelo conceitual.

2. Princípios

O modelo de dados deverá:

representar fielmente o domínio de negócio;
evitar redundância desnecessária;
favorecer consistência;
permitir evolução futura;
suportar múltiplos tenants;
suportar milhões de registros;
permitir auditoria completa;
permitir versionamento quando necessário.

4. Entidades Fundamentais

As seguintes entidades fazem parte do núcleo da plataforma.

Tenant

Representa um cliente da plataforma.

Exemplos:

Administrador
Empresa administradora
Imobiliária

Responsável por isolar completamente os dados.

Usuário

Pessoa autenticada.

Pode possuir um ou mais papéis.

Exemplos:

Administrador

Operador

Faxineira

Proprietário

Papel

Define responsabilidades.

Não armazena regras de negócio.

Relaciona-se com permissões.

Permissão

Representa uma ação autorizada.

Exemplos:

Editar imóvel.

Excluir reserva.

Visualizar dashboard.

5. Estrutura Imobiliária
Condomínio

Representa o condomínio físico.

Possui:

endereço;
portarias;
regras;
observações;
contatos;
integrações próprias (quando existirem).

Um condomínio poderá possuir diversos imóveis.

Portaria

Representa um ponto de acesso.

Pode existir mais de uma.

Exemplos:

Portaria principal.

Portaria de serviço.

Portaria remota.

Cada portaria poderá possuir:

telefone;
WhatsApp;
horários;
regras;
mensagens automáticas.
Grupo de Imóveis

Permite agrupar imóveis.

Exemplos:

Studios.

Lofts.

Praia.

Centro.

Luxo.

Tem como objetivo compartilhar configurações.

Imóvel

Principal ativo da plataforma.

Possui:

identificação;
condomínio;
grupo;
localização;
capacidade;
políticas;
configurações;
fechadura;
instruções;
calendário.
Fechadura

Representa o mecanismo de acesso.

Não pressupõe tecnologia específica.

Pode ser:

Senha fixa.

Senha dinâmica.

Token.

API.

Bluetooth.

RFID.

Outras tecnologias futuras.

checkout;

mensagens;
ocorrências.

17. Regras de Consistência

O modelo deverá respeitar obrigatoriamente:

nenhuma entidade pertence a mais de um Tenant;
nenhuma reserva existe sem um imóvel;
nenhuma hospedagem existe sem uma reserva;
nenhuma faxina existe sem um imóvel;
nenhuma conversa existe sem uma origem;
nenhuma auditoria pode ser alterada;
nenhum evento poderá ser apagado fisicamente.
18. Exclusão de Dados

O sistema deverá privilegiar:

arquivamento;
desativação;
versionamento;
exclusão lógica (soft delete).

Exclusão física deverá ocorrer apenas quando realmente necessária ou exigida por legislação aplicável.

19. Histórico

As seguintes entidades deverão manter histórico completo:

imóveis;
reservas;
hóspedes;
faxinas;
configurações;
políticas;
templates;
integrações;
workflows;
mensagens.
20. Versionamento

Sempre que aplicável, o sistema deverá manter versões para:

políticas;
templates;
configurações;
prompts;
workflows.

O histórico de versões deverá permitir auditoria, comparação e eventual restauração.

21. Evolução do Modelo

O modelo deverá ser preparado para incorporar novas entidades sem necessidade de reestruturação significativa.

Exemplos futuros:

contratos;
manutenção preventiva;
fornecedores;
inventário do imóvel;
precificação dinâmica;
gestão financeira;
tarefas operacionais;
seguros;
múltiplas equipas de limpeza.
22. Estratégia de Persistência

Cabe ao Claude Code definir o modelo físico mais adequado, podendo utilizar diferentes tecnologias de armazenamento conforme a natureza dos dados (transacionais, cache, busca, arquivos e analytics).

Independentemente da tecnologia escolhida, o modelo deverá garantir:

consistência transacional onde necessária;
elevada performance;
facilidade de evolução;
baixo custo operacional;
alta disponibilidade;
suporte a consultas eficientes;
capacidade de crescimento sem refatorações estruturais.
23. Considerações Finais para o Claude Code

Este documento representa o modelo conceitual do domínio, e não um esquema físico de banco de dados.

A implementação deverá respeitar os conceitos aqui definidos, mas o Claude Code terá autonomia para decidir:

o(s) tipo(s) de banco(s) de dados mais adequados;
a normalização ou desnormalização quando justificável;
índices;
chaves;
relacionamentos físicos;
estratégias de particionamento;
otimizações de leitura e escrita.

As decisões deverão priorizar escalabilidade, simplicidade, consistência e facilidade de manutenção, preservando a integridade do domínio de negócio definido para o iHostPro.
