# ADR-016 — Tenant-safe Execution Boundary for Persistent Wolverine Consumers

Status: Aceito
Data: 2026-08-12

## Contexto

**Housekeeping (Fase 6, ADR-015).** Uma homologação real (`ReservationCancelledWorkerRoundTripTests`, RabbitMQ real, Postgres real, Worker real subprocess) revelou que, durante o processamento real de uma mensagem pela cadeia Wolverine, `HousekeepingDbContext` era materializado com uma instância de `ITenantContext` **diferente** da que `TenantResolutionMiddleware` efetivamente resolveu para aquela mensagem — o Global Query Filter tenant-aware do EF Core (fail-closed por design, `BaseDbContext.BuildTenantFilter`) produzia `WHERE FALSE` em toda query, e a reação de negócio silenciosamente não encontrava nada para agir. ADR-015 corrigiu isso introduzindo `IHousekeepingMessageExecutionScope`: um child DI scope explícito, aberto uma única vez por mensagem, que resolve `ITenantContext` **desse mesmo scope** e o resolve para o `tenantId` (lido diretamente do próprio `IntegrationEvent`) **antes** de resolver o processor de negócio — garantindo que `HousekeepingDbContext`/o transaction executor, resolvidos depois a partir do mesmo scope, observem a mesma instância.

**Reservations (Fase 7, Incremento 1 — Agenda Foundation, Checkpoint 1 CLOSURE).** Reservations tornou-se, neste checkpoint, o primeiro *persistent Wolverine consumer* deste Bounded Context (os dez eventos de ciclo de vida de `Cleaning`, publicados por Housekeeping, mantendo `CleaningScheduleProjectionEntry` sincronizada). O desenho original deixava Wolverine resolver `CleaningScheduleProjectionSynchronizer` (e, transitivamente, `ReservationsDbContext`) diretamente pela sua própria cadeia gerada, sem nenhum boundary equivalente ao de Housekeeping — decisão registrada explicitamente no Checkpoint 1 original como aceitável até prova em contrário via um gate real de transporte.

Um segundo gate real de transporte (`CleaningNeedsHelpScheduleProjectionWorkerRoundTripTests`, exercitando Create → Assign → Start → NeedsHelp) revelou que `CleaningAssigned` nunca atualizava a projeção. Uma investigação exaustiva, em múltiplas rodadas com evidência obrigatória a cada etapa (ver Fase 7 - Agenda Foundation - Validacao e Homologacao.md, §Investigação Checkpoint 1 CLOSURE, para a narrativa cronológica completa), primeiro descartou rigorosamente uma "commit-visibility race" (o próprio retry nativo do Wolverine, 7 tentativas reais em ~7,6s, não resolvia o problema) e a hipótese `OverrideStorage`/middleware de transação EF (decompilação real de `Wolverine.EntityFrameworkCore.dll`/`Wolverine.dll` 6.22.0 confirmou que `OverrideStorage` apenas reatribui `Storage`, e que as cadeias geradas reais de `CleaningCreatedHandler`/`CleaningAssignedHandler` são estruturalmente **idênticas**, byte a byte) — descartando as hipóteses A/B/C originalmente cogitadas.

A causa real, reproduzida em um harness rápido in-process (dispatch pela cadeia Wolverine real via `IMessageBus.InvokeAsync`, sem RabbitMQ) e comprovada por evidência SQL direta, é **exatamente o mesmo mecanismo do ADR-015**: a cadeia gerada resolve `ReservationsDbContext` via `GetRequiredService<ReservationsDbContext>(serviceScope.ServiceProvider)` dentro de um `IServiceScope` próprio, recém-criado (`_serviceScopeFactory.CreateAsyncScope()`) — o `ITenantContext` injetado nesse `ReservationsDbContext` (e fechado pelo closure do Global Query Filter, `BaseDbContext.OnModelCreating`) é uma instância **diferente** da que `TenantResolutionMiddleware.Before(context, tenantContext)` populou, porque essa segunda instância é um `new TenantContext()` manual, declarado separadamente pelo código gerado e usado apenas para `ReservationsOutboxTransactionExecutor`/`TenantAwareTransactionScope`'s `SET LOCAL app.tenant_id` (RLS).

SQL real capturado confirma isso de forma inequívoca:

```
-- CleaningCreated (AnyAsync de idempotência):
SELECT FALSE

-- CleaningAssigned (FirstOrDefaultAsync do UpdateAsync):
SELECT c.tenant_id, c.cleaning_id, ...
FROM reservations.cleaning_schedule_projection AS c
WHERE FALSE
```

O RLS (`SET LOCAL app.tenant_id`) estava correto durante toda a investigação — usa a instância corretamente resolvida. O Global Query Filter estava corretamente fail-closed (por design, ADR-003) — apenas observando a instância errada, permanentemente não resolvida. `CleaningCreated` mascarava o defeito porque `Add()`/`INSERT` não é afetado por Global Query Filters; `CleaningAssigned`, ao depender de `FirstOrDefaultAsync` (uma leitura filtrada), expunha o defeito de forma determinística — não uma race, e nenhuma quantidade de retry o resolveria. Uma consequência colateral real, até então não descoberta, foi encontrada e corrigida junto: o próprio guard de idempotência de `CleaningCreated` (`AnyAsync`) sofria do mesmo `WHERE FALSE`, o que faria uma redelivery real do mesmo `CleaningCreated` tentar um segundo `INSERT` contra a chave primária composta (`tenant_id, cleaning_id`) e lançar `DbUpdateException`, ao invés do no-op idempotente que seu próprio comentário prometia.

## Alternativas Rejeitadas

1. **Sincronizar manualmente as duas instâncias de `ITenantContext`** (ex.: propagar o `tenantId` já resolvido para a instância que o EF usa, por algum hook). Rejeitada: trata o sintoma, não a causa — a arquitetura correta é impedir que duas instâncias independentes participem do mesmo processamento de negócio, não coordená-las manualmente.
2. **Abstração genérica compartilhada agora** (`IMessageExecutionScope<TContext>`, `TenantAwareWolverineExecutionScope<T>`, `WolverineTenantScopeFactory` em BuildingBlocks). Rejeitada nesta etapa por decisão explícita: dois Bounded Contexts (Housekeeping, Reservations) apresentando o mesmo padrão ainda não justificam automaticamente uma abstração comum — a duplicação arquitetural entre `IHousekeepingMessageExecutionScope` e `IReservationsMessageExecutionScope` é deliberada. Uma abstração comum pode ser avaliada futuramente se um terceiro Bounded Context apresentar a mesma necessidade.
3. **Retry (manual ou `RetryWithCooldown` do Wolverine), `Task.Delay`, aumento de prefetch/redução de concorrência.** Rejeitadas: o defeito comprovadamente não é transitório — nenhuma quantidade de espera o resolve, porque a instância de `ITenantContext` do EF nunca é populada, independentemente do tempo decorrido (confirmado pelo próprio experimento de retry nativo do Wolverine, 7 tentativas/~7,6s, antes desta correção).
4. **Upsert cego, seed direto, `IgnoreQueryFilters`, ou desabilitar/alterar o fail-closed do `BaseDbContext`.** Rejeitadas: mascarariam o sintoma sem corrigir a causa, e a segunda alternativa especificamente enfraqueceria a garantia de isolamento multi-tenant (ADR-003) para todo o resto da aplicação, não apenas para este consumer.
5. **`AsyncLocal`, `ITenantContext` singleton/estático, Wolverine Conjoined Tenancy, um segundo processo Worker, ou um novo `DbContext` só para este consumer.** Rejeitadas sem experimentação — mudariam responsabilidades arquiteturais já estabelecidas (mesma classe de rejeição já registrada pelo ADR-015 para Conjoined Tenancy) sem necessidade: o boundary local resolve o problema sem alterar nenhuma dessas responsabilidades.

## Decisão

Generaliza-se o princípio do ADR-015: **qualquer *persistent Wolverine consumer*** — um handler que combina `BaseDbContext`, um `ITenantContext` escopado próprio, e Global Query Filters tenant-aware do EF — **não deve permitir que o codegen do Wolverine materialize, direta ou transitivamente, o grafo de dependências de negócio (DbContext, transaction executor, processors) usando uma instância de `ITenantContext` independente da que `TenantResolutionMiddleware` efetivamente resolveu**. A correção é uma *context-local execution boundary*, não uma abstração genérica (ver Alternativa Rejeitada 2).

Para Reservations, isso significa: `IReservationsMessageExecutionScope` (Application) / `ReservationsMessageExecutionScope` (Infrastructure.Messaging) — mesmo desenho de `IHousekeepingMessageExecutionScope`/`HousekeepingMessageExecutionScope`: abre um child DI scope (`IServiceScopeFactory.CreateAsyncScope()`) por mensagem, resolve `ITenantContext` **desse** scope, chama `.SetTenant(tenantId)` (tenantId lido diretamente de `IntegrationEvent.TenantId` pelo adapter, nunca do `ITenantContext` ambiente do Wolverine) **antes** de resolver `IIntegrationEventHandler<TMessage>` — `ReservationsDbContext`/`ReservationsOutboxTransactionExecutor`, resolvidos depois do mesmo scope via injeção de construtor ordinária, portanto observam a mesma instância, inteiramente fora da resolução de DI por-mensagem do Wolverine.

Os dez adapters Wolverine de Reservations (`CleaningCreatedHandler`, `CleaningAssignedHandler`, `CleaningInTransitHandler`, `CleaningStartedHandler`, `CleaningInspectionStartedHandler`, `CleaningCompletedHandler`, `CleaningInterruptedHandler`, `CleaningNeedsHelpHandler`, `CleaningNeedsMaterialHandler`, `CleaningCancelledHandler`) dependem exclusivamente de `IReservationsMessageExecutionScope` (mais `MessageContext`/`CancellationToken`) — nunca de `ReservationsDbContext`, `IReservationsTransactionExecutor` ou `CleaningScheduleProjectionSynchronizer` diretamente. `opts.CodeGeneration.AlwaysUseServiceLocationFor<IReservationsMessageExecutionScope>()`, registrado uma única vez em `IHostPro.Worker/Program.cs`, é a mesma exceção pontual de codegen (não um Service Locator na aplicação) que ADR-015 já registrou para `IHousekeepingMessageExecutionScope` — necessária porque `ReservationsMessageExecutionScope` depende de `IServiceScopeFactory` (Singleton), que o codegen estrito do Wolverine rejeita por padrão.

**Este boundary não é obrigatório para todo handler Wolverine.** Não é necessário para consumers que não atravessam `BaseDbContext`/Global Query Filters tenant-aware — `PolicyUpdatedCacheInvalidation` (Configuration & Policy), que depende apenas de `IPolicyCacheInvalidator` (um cliente Redis puro), permanece com seu desenho direto, sem alteração, exatamente como ADR-015 já registrou.

## Consequências

### Positivas
- Elimina o `WHERE FALSE` indevido: a mesma identidade de `ITenantContext` alimenta o Global Query Filter do EF e o `SET LOCAL app.tenant_id` do RLS.
- Preserva o fail-closed do `BaseDbContext` intacto — a correção é a identidade da instância observada, nunca o comportamento do filtro em si.
- Corrige, como efeito colateral comprovado, a idempotência real de `CleaningCreated` (antes falsamente propagandeada como no-op; uma redelivery real teria lançado `DbUpdateException`).
- Mantém o código Wolverine externo (os dez adapters) livre de qualquer tipo de persistência — reforça, por teste de arquitetura (`ReservationsMessageExecutionScopeArchitectureTests`, mirror exato de `HousekeepingMessageExecutionScopeArchitectureTests`), que `ReservationsMessageExecutionScope` é a única classe de Reservations autorizada a depender de `IServiceScopeFactory`.
- Prova de causalidade completa: o toggle real (spike isolado em `CleaningAssignedHandler`, antes/depois, via o harness de dispatch real rápido) mudou o SQL observado de `WHERE FALSE` para um predicado `WHERE tenant_id = ... AND cleaning_id = ...` real, com a linha sendo encontrada e atualizada corretamente — `CleaningCreated`, ainda não migrado nesse momento, permaneceu como controle positivo mostrando o defeito mascarado intacto.

### Riscos Aceitos
- Duplicação arquitetural deliberada entre `IHousekeepingMessageExecutionScope` e `IReservationsMessageExecutionScope` (ver Alternativa Rejeitada 2) — aceita nesta etapa; uma abstração comum pode ser avaliada se um terceiro Bounded Context repetir a necessidade.
- Um child DI scope deliberado por mensagem introduz `IServiceScopeFactory` em mais um ponto único da aplicação — mitigado pelo mesmo padrão de teste de arquitetura já usado para Housekeeping.
- Mais código de integração do que o caminho "feliz" padrão do Wolverine — aceito como custo necessário para preservar o modelo de tenancy/RLS já estabelecido (ADR-003), mesma decisão do ADR-015.
- Durante a validação deste checkpoint, `PolicyUpdatedRegressionTests` mostrou-se intermitentemente flaky (falhando ~2 de 3 execuções com a geração do cache Redis avançando 2x em vez de 1x para um único evento). Isolado por experimento controlado (removendo e restaurando apenas a linha `AlwaysUseServiceLocationFor<IReservationsMessageExecutionScope>()`): a falha reproduz-se identicamente com ou sem essa linha — **não é uma regressão desta correção**. É consistente com o risco já documentado e aceito pelo próprio ADR-015 (nenhum inbox durável sob `EndpointMode.Inline`; uma redelivery real do RabbitMQ é aceita e reprocessada). Não corrigido nesta etapa — fora do escopo desta decisão.
